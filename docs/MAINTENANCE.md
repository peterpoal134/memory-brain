# 个人本机维护：升级与恢复

本版支持人工确认的并排维护，不自动覆盖旧环境。下面使用的路径和账号都是使用者自己的；不要把私人配置、备份、口令或 DPAPI 文件发进聊天/仓库。先读完再操作。

本页适用于 `0.2.4` 框架正式版，插件与内核均为 `0.2.4`。升级仍以保留现有数据、配置和回退路径为原则；当前发布定位与验证范围见 [发布说明](RELEASE-0.2.4.md)。

## 备份范围

面板的在线备份 ZIP 包含 `brain.db`、`preferences.json` 和 `manifest.json`，数据库由 SQLite 在线备份接口生成，可以包含尚在 WAL 中的已提交内容。它不是整个运行环境的备份：不包含模型凭据、运行配置、队列、宿主 profile、外部人格文件、Windows 登录身份或模型权重。

此外在本机安全保存：当前插件代码/旧内核 wheel；原 `private/config.json`；如有，原 `private/model-secrets.dpapi`、`private/host.json` 和数据目录的 `profile-sources.json`；原 DSH 接入配置；原队列目录及其状态。人格/准则如引用外部文件，要另行保留这些源文件。DPAPI 备份通常只供原 Windows 账号解密；换电脑/账号需要重新配置自己的模型密钥。

不要只复制正在写入的 `brain.db` 主文件，它不一定包含 WAL 中的已提交数据。也不要把旧备份恢复到仍在运行的数据库旁。

## 并排升级

1. 从当前面板创建在线备份并下载，检查 ZIP CRC、manifest 记录和数据库 `PRAGMA integrity_check`。本版备份manifest没有SHA-256清单；如你另存过归档校验值，才用它比对归档SHA-256。核对原 `owner`、数据目录、消息数量，保存上述独立配置材料。
2. 暂停 DSH 中该记忆插件采集，确认 pending 队列已排空、没有未处理 failed；存在积压时先保留现场处理，不继续切换。正常停止旧内核，确认原端口已释放、旧 PID 已结束。查询失败、401、超时都不能证明服务停止。
3. 将完整新包解压到另一个固定目录。不要覆盖旧目录，不要移动原数据库。只建立新 `.venv` 并离线安装新 wheel；**本步骤不要运行会创建新空配置的首装入口**。在新目录执行：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -I -m pip install --no-index --find-links .\wheels --only-binary=:all: xiaojiu-brain==0.2.5
```

4. 保留原配置文件的原位置，使其相对 `data_dir`、owner、口令与模型环境变量约定都不改变。使用新目录解释器配原配置启动，`<原配置绝对路径>` 换成真实路径：

```powershell
.\.venv\Scripts\python.exe -I -m xiaojiu_brain --config '<原配置绝对路径>' start
.\.venv\Scripts\python.exe -I -m xiaojiu_brain --config '<原配置绝对路径>' status
```

若原环境通过启动器从 DPAPI 注入模型密钥，这个直接命令不会替你解密密钥；维护者应保留原启动器的安全注入步骤，只把其解释器指向新 `.venv`。不要把密钥改写到命令行。本步骤未配置密钥时，可以验证原话/词法路径，不能说远程整理已恢复。

5. 核对返回版本 `0.2.5`、原 owner 和原数据数量；用一条非敏感合成信息验证原话、出处、重复投递，再修改 DSH 插件条目为新包目录，并显式设置 `brainConfigFile` 为原配置绝对路径。保留原 queueNamespace、数据目录。更换条目前确保旧条目已卸载，避免双重采集。
6. 这时属于显式配置安装，不是首次设置管理器自动升级。外部配置需要手动启动对应新内核，桌面/开机启动器也须明确使用新解释器和原配置；不要指望仅更新插件就自动升级 Python。
7. 回退时暂停采集、正常停止新内核，再使用旧解释器、旧插件和原配置启动；保留同一份现有数据，不把旧快照覆盖回去抹掉切换后原话。RC3 首次打开数据库会增加用于排序的 SQLite 索引，可能短暂消耗时间与磁盘；索引不删除原数据。回退兼容仍须先在备份副本验证，未来版本须另查迁移兼容性。

## 从在线备份手动离线恢复

本版没有 restore HTTP/CLI 命令。以下是手动恢复，不是“一键恢复通过”。

1. 保留原坏库和队列现场，停止其采集与内核，确认进程/端口已停。先备份恢复目标里仍有价值的新原话；恢复旧快照会回到快照时间点，后续对话不能凭空重建。
2. 将 ZIP 解到**全新的恢复目录**，拒绝含绝对路径、`..` 或符号链接的条目。检查 ZIP CRC、manifest 中的版本/构建与记录范围，运行 SQLite `PRAGMA integrity_check` 与 `PRAGMA foreign_key_check`。备份manifest不含文件SHA-256清单；只有在另存了可信外部归档SHA-256时才比对它。ZIP CRC与SQLite完整性不能单独认证备份来源。本版预期数据库、preferences 和manifest，不执行备份内任何脚本。
3. 用独立配置指向新恢复目录，沿用原 owner；保留原配置以便回退，不在原数据库上混入备份。不要从旧目录复制 `brain.db-wal`/`brain.db-shm` 到恢复目录。确认恢复目录没有来自其他库的 WAL/SHM。
4. 使用匹配内核启动恢复库，核对消息/记忆数量、原话逐字、来源引用、删除状态与保密限制。preferences 应恢复；`profile-sources.json` 及其外部文件、模型密钥等只从你另存的本机材料恢复。缺这些文件不能算全环境已恢复。
5. 切换插件到恢复配置前先停原条目并明确处理队列。备份时点之后的待发记录可以重放，但不得无条件重放整份旧会话以抵消已执行的删除。原库和旧环境保留到核验完成；恢复不是删除旧数据的授权。

## 重启、故障与支持范围

进程停止/杀进程后恢复与整机重启不是同一项验收。若当前记录只验证服务重启，就如实标记“整机重启待验”。本机观察期间记录队列积压、失败任务、错误类别、检索耗时和资源变化；不需要重复跑整套记忆题。

本版按框架与参考实现正式发布，长期日常观察、普通与低配机器负载、更多模型组合的验证记录在后续补充，未列为本次发布的前置条件。已做的程序检查、隔离接入与单机维护验证按各自范围报告；后续应分别记录记忆内核、向量模型和聊天模型的资源占用，避免将整套模型负载算作框架本身。

已记录的维护验证范围为 Windows 个人本机、低并发。同账号工具进程不是强隔离边界。Android DSHA、多用户服务、跨电脑凭据迁移与其它系统的完整宿主流程需另行验收。


## 0.2.4 资源索引兼容

升级首次启动会流式核对旧去重日志，并建立本机磁盘索引。不要删除旧日志、pending、failed、恢复队列或原始会话日志。索引只减少常驻内存，不减少已保存记忆；磁盘占用仍随历史增加。新旧版本不能同时写同一个队列目录。回退前先停新适配器，再保留整个队列目录切回旧版；旧日志仍为回退保留，不能仅复制数据库。详见[资源管理](RESOURCE-MANAGEMENT.md)。
