# 后台整理：批量、等待与用量

原话归档、向量索引和摘要/事实整理分开调度。调整整理频率不应让原话等待摘要，也不应拖延已启用的向量索引；模型暂不可用时原话仍保留。

## 调度设置

| 字段 | 默认 | 有效值 | 含义 |
|---|---:|---|---|
| `derive_batch_messages` | 12 | 整数 1～12 | 一批最多处理的消息数；12 条通常约 6 个完整回合 |
| `derive_max_wait_seconds` | 900 | 整数 30～86400 | 不足批量时的最长积累时间，达到后可在检查中发起整理 |
| `derive_interval` | 5 | 有限数值 1～600 | 整理检查间隔，单位秒；不是嵌入索引的运行间隔 |

批量字段拒绝浮点、字符串、布尔值和越界值。服务不会为无效设置部分保存同一更新里的其它项。没有新字段的旧 `preferences.json` 会补入默认值，并保留已有设置、自我笔记、表达偏好和情绪状态；旧配置文件也可继续加载。

设置可在“维护与备份”修改，仍使用现有 `PATCH /v1/settings`：

```json
{
  "derive_batch_messages": 12,
  "derive_max_wait_seconds": 900,
  "derive_interval": 5
}
```

待整理消息满足批量或达到最长等待后才调用整理模型。实际开始时间还受检查时机、模型可用性、失败重试及会话/使用边界分组影响。关闭整理不停止原话归档；关闭语义索引则不产生可用的新向量，但不影响词法检索。这些设置不承诺费用、固定节省倍数或所有对话都能以同样大小整理。

凑批按同一使用者、同一会话和相同披露等级/主题分别计算；不会把不同会话拼成一批。积累时间以本次进入队列的时间计算，不把历史原话日期当成已经等待的时间。原话向量有独立线程，整理变慢或等待凑批不会阻塞新原话索引。

## 截断与失败

输入多条消息超过当前输入预算时先拆批；模型明确返回输出长度截断时再二分重做。每个成功子批独立提交，并保留未完成部分的拆批大小，重启后不会重新合成已知过大的父批。原话与来源校验不放宽，输入不会悄悄截掉；单条超过64,000字符或单条整理仍输出截断，会留下明确失败记录，原话仍保留并可检索。

来源校验等错误仍拒绝整子批，普通自动重试最多3次。已经开始的请求可完成；关闭整理或停止服务后不会再发送下一子批。`run_once()`是显式维护兼容入口，会强制处理一批；正常后台调度只使用带批量/等待门槛的入口。

## 后台整理用量

`GET /v1/status` 可返回 `model_usage`，面板以服务实际返回值显示：

| 字段 | 含义 |
|---|---|
| `attempts` | 后台整理模型调用尝试次数，包含失败尝试 |
| `reported_responses` | 有可计用量记录的响应数 |
| `input_tokens` / `output_tokens` | 已收到并记录的输入/输出 token 数 |
| `cache_hit_tokens` / `cache_miss_tokens` | 已报告的缓存命中/未命中 token 数 |
| `unknown_usage_attempts` | 未收到可计用量的尝试数；不能当作 0 tokens |
| `by_outcome` | 后台整理尝试的处理结果分类 |

这里不统计聊天、向量嵌入、测评作答或判卷；重试可能增加尝试次数。即使整理结果解析失败，已返回的 provider 用量仍可能真实发生。超时或传输断开而没有 usage 的部分，只标为未知，不填估计 tokens，不计算金额。累计范围以服务保留的用量记录为准，旧版本未记录的调用不补估。

服务端没有 `model_usage` 时面板显示“暂无后台整理用量记录”；只缺某个字段时显示“未报告”，不把缺失值转换为 0，也不因混合版本报错。仅当服务明确返回数字 0，才显示 0。

每次实际请求尝试都记录安全关联ID、数量、耗时、结果分类和已报告usage；不写提示词、回答正文、请求头、密钥或完整私话。账本写入失败会暂停后续付费整理，原话入库和向量处理继续；修复存储后需要重新启动服务恢复整理。新账本从升级后的记录开始，旧版本没有保留的52次等调用不会被补估为精确token数。
